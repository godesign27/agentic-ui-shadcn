# System Architecture

This document describes the architecture of the Agentic AI UI Control System, including the instruction layer stack, read flow, implementation contracts, and multi-framework model.

## Instruction Layer Stack

The Agentic AI UI Control System uses a layered governance approach:

### Layer 1: Core Governance (This Repository)
The foundational layer that defines:
- Behavioral rules and constraints (AGENT_RULES.md)
- Design principles and decision frameworks (DESIGN_PRINCIPLES.md)
- Accessibility requirements (ACCESSIBILITY.md)
- Token system contracts (TOKENS_REFERENCE.md)
- Theming contracts (BRAND_THEMING.md)
- System architecture (this document)

This layer is framework-agnostic and applies to all implementations.

### Layer 2: Implementation Repository
Framework-specific repositories (e.g., `agentic-ui-bootstrap`) that provide:
- Component library and snippets
- Framework-specific patterns
- Example implementations
- Token mappings to framework systems
- Component index and documentation

This layer translates core governance into framework-specific implementations.

### Layer 3: Generated Code
The actual UI code generated by agents following the rules and principles from Layers 1 and 2.

## Read Flow

Agents must follow this read flow when generating UI code:

### Phase 1: Core Documentation (This Repository)
1. **README.md** - Understand the system overview and navigation
2. **SYSTEM_ARCHITECTURE.md** (this file) - Understand the system structure
3. **AGENT_RULES.md** - Learn mandatory behavioral constraints
4. **DESIGN_PRINCIPLES.md** - Understand the decision framework
5. **ACCESSIBILITY.md** - Learn accessibility requirements
6. **TOKENS_REFERENCE.md** - Understand the token system
7. **BRAND_THEMING.md** - Learn theming and brand integration rules

### Phase 2: Implementation Repository Documentation
1. **COMPONENTS_INDEX.md** - Review available components
2. **Component documentation** - Read relevant component docs in `/components`
3. **Pattern documentation** - Review relevant patterns in `/patterns`
4. **Example documentation** - Study similar examples in `/examples`
5. **Token documentation** - Understand framework-specific token mappings
6. **Brand theming documentation** - Learn framework-specific brand integration

### Phase 3: Code Generation
After completing Phases 1 and 2, agents can generate code that:
- Follows all rules and principles
- Uses only components from the index
- Meets accessibility requirements
- Uses tokens appropriately
- Respects theming rules

## Implementation Repo Contract

All implementation repositories must provide the following structure and documentation:

### Required Files

#### COMPONENTS_INDEX.md
A comprehensive index of all available components, including:
- Component name and description
- Usage guidelines
- Accessibility notes
- Token dependencies
- Related components

Agents must verify component availability in this index before use.

### Required Directories

#### /components
Directory containing:
- Component snippets (reusable code examples)
- Component documentation (usage, props, variants)
- Component-specific accessibility notes
- Component token requirements

Structure: Each component should have its own file or subdirectory with documentation and examples.

#### /patterns
Directory containing:
- Common UI patterns (e.g., "form with validation", "data table with sorting")
- Pattern documentation explaining when to use each pattern
- Pattern examples showing implementation
- Pattern accessibility considerations

Patterns are compositions of components that solve common problems.

#### /examples
Directory containing:
- Complete page examples
- Example documentation explaining the example's purpose
- Example accessibility notes
- Example token usage

Examples demonstrate real-world usage of components and patterns.

#### /styles (or /tokens or /overrides)
Directory containing:
- Token definitions and mappings
- Brand token integration examples
- Theme mode configuration
- Custom style overrides (if applicable)

The exact structure varies by framework, but must document how tokens map to framework-specific implementations.

### Optional but Recommended

- **README.md**: Overview of the implementation repository
- **GETTING_STARTED.md**: Quick start guide for the implementation
- **MIGRATION.md**: Guide for migrating from other systems (if applicable)

## Multi-Framework Model

The Agentic AI UI Control System supports multiple framework implementations:

### Bootstrap Implementation (`agentic-ui-bootstrap`)
- Uses Bootstrap's component system and utilities
- Maps tokens to Bootstrap CSS custom properties or Sass variables
- Provides Bootstrap-specific patterns and examples
- Supports Bootstrap's theming mechanism

### shadcn Implementation (`agentic-ui-shadcn`) [Future]
- Uses shadcn/ui component patterns
- Maps tokens to shadcn's CSS variable system
- Provides shadcn-specific patterns and examples
- Supports shadcn's theming approach

### Material Implementation (`agentic-ui-material`) [Future]
- Uses Material Design components
- Maps tokens to Material Design tokens
- Provides Material-specific patterns and examples
- Supports Material's theming system

### Custom Design System [Future]
- Supports custom design systems
- Requires implementation repository to provide component index and token mappings
- Follows same contract as framework implementations

## Framework-Agnostic Principles

While implementations are framework-specific, the core system remains framework-agnostic by:

1. **Abstracting concepts**: Describing patterns conceptually (e.g., "utility-first spacing") rather than framework-specifically (e.g., "Bootstrap utility classes")
2. **Token contracts**: Defining token requirements without specifying implementation details
3. **Behavioral rules**: Enforcing rules that apply regardless of framework
4. **Accessibility standards**: Requiring WCAG compliance regardless of framework
5. **Design principles**: Providing decision frameworks that work across frameworks

## Agent Responsibilities

Agents using this system must:

1. **Read in order**: Follow the read flow exactly as specified
2. **Verify components**: Check COMPONENTS_INDEX.md before using any component
3. **Compose, don't invent**: Use existing components and patterns
4. **Respect constraints**: Follow all rules in AGENT_RULES.md
5. **Ensure accessibility**: Meet all requirements in ACCESSIBILITY.md
6. **Use tokens**: Follow TOKENS_REFERENCE.md for all values
7. **Support theming**: Respect BRAND_THEMING.md rules

## System Boundaries

This system defines **what** and **how** agents should generate UI code, but does not:
- Provide the actual UI components (implementation repositories do)
- Define build tooling or dependencies (implementation repositories do)
- Specify deployment strategies
- Define API contracts or backend requirements
- Specify testing strategies (though accessibility testing is encouraged)

The system focuses exclusively on the governance and instruction layer for UI code generation.
